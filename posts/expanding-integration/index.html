Expanding Integration: Using the Whole Machine to Upgrade to 180B

TL;DR: Qwen3.8-Flash-Next — 177B total, ~3B active — at UD-IQ4_XS, 196,608 context, on the same $376 Radeon Pro V620. It does not fit in 32 GB of VRAM. It does not fit in 32 GB of RAM either. It fits because the machine stops pretending VRAM is the only memory: ~21 GiB of hot experts in the card, ~34 GiB of warm experts pinned in RAM, the rest streamed from an NVMe, with a second GPU running the small models and the CPU running the vision encoder. Prefill at 90K went from 194–222 tok/s to ~750, decode from ~13 to 26–40 tok/s, and the eval harness from 0.75 to 0.88–1.00. The upgrade was a 64 GB RAM kit, a memlock ceiling, and a serving engine that treats the whole box as one cache — not a bigger graphics card.

The 27B was never slow

The first post ended with a 2020 VDI card decoding a 27B Q6 model at 30.5–32.2 tok/s with a 192K context, for $376 all in. That number is still real. What changed is what I was asking it to do.

The 27B is a dense model. Every token runs through all 27 billion parameters, which is why it is fast and predictable — and why it has a ceiling. On the same nine-task harness I use to compare local models, it scored 0.75. It got the three-word instruction, the JSON keys, the code fix, both Godot tasks, and a 50K-token needle. It missed the two tasks that needed actual reasoning: the maximum-cuts puzzle (it answered 8; the answer is 7) and the pump arithmetic (1.2 instead of 2.0). Its config also runs --reasoning off, because chain-of-thought was costing 50–100 tokens per answer and I was optimizing tok/s like an idiot.

And the 27B’s setup has no eyes. No vision projector, no second opinion, no way to look at a screenshot of the game it just wrote. For a coding agent that is a bigger deal than the benchmark score.

What a “180B” model actually means

Qwen3.8-Flash-Next is 177B parameters total, with about 3B active per token. Round it to 180B for the title; the router only fires a slice of the experts on any given token. That is why a model 6.5× larger than the 27B can decode at the same order of speed: per-token compute is in the same class, and the rest is memory bandwidth.

There is a second wrinkle that matters more than the parameter count. About 51B of those parameters are not conventional weights at all — they are a per-layer n-gram lookup table (the PLE), a giant embedding that is mostly cold. In the UD-IQ4_XS build it is packed into the same 87.25 GiB file, but the hot set is much smaller than the file.

Tier Capacity What lives there Why
V620 VRAM 32 GB ~21.19 GiB expert cache + KV cache + activations the experts the router actually hits, per token
System RAM 64 GB 34.31 GiB of experts, page-locked (33.04 after the vision/KV change) the next-most-likely experts, one PCIe hop away
NVMe 87.25 GiB model cold experts and the PLE table streamed on demand; the long tail
RX 9060 XT 16 GB Qwen3-8B subagents, Gemma vision keeps the agent alive while the V620 is claimed
CPU 16 threads vision encoder, some prefill the parts that do not need a GPU

That table is the whole article. The model is 87 GiB. The machine has 32 GB of VRAM, 64 GB of RAM, 16 GB of second-GPU VRAM, and 87 GB of fast disk. Nothing individually fits it; the hierarchy does.

The upgrade, in order

1. The RAM, because the card was starving

The first version ran with 32 GB of system RAM and an 8 GiB page-locked expert tier. It worked, barely: prefill 194–222 tok/s at 90K, decode ~13 tok/s, and one crash in three under sustained long-context load. The crashes were not thermal — a repaste and a stock-voltage run had already proven that, with a failure at 52 °C junction and 187 W. They were host memory pressure: the kernel reclaiming pages the GPU had pinned.

The 64 GB kit (4 × 16 GB DDR4) changed the operating point. 62.7 GiB usable, all four sticks seen, no MCE, no EDAC, no amdgpu faults. But the BIOS came up on JEDEC defaults — 29 GB/s, which is DDR4-2133, not the 2933 the kit is rated for. DOCP did not survive the DIMM change. That is still on the list.

The tier went 8 → 30 → 35 GiB. At 30 GiB the engine logged 13,289 of 34.31 GiB resident and still read 25.4 GiB from disk. At 35 GiB it pinned the whole pool:

FileExpertSource: mapped pinned cache complement ready: resident 34.31 GiB, pinned 34.31 GiB

That required raising the hard RLIMIT_MEMLOCK from 32 GiB to 40 GiB — asking for more than the limit does not fail loudly, it just silently declines to pin. The unit got LimitMEMLOCK=40G, the running user manager got prlimited, and the engine got --resident-budget-gib 35.

The only new part in this whole upgrade was the 64 GB kit: under $200 (~$3.13/GB for a matched 4 × 16 GB DDR4-3000 set). The V620, the 9060 XT, and the NVMe were already in the box. The 180B did not cost $1,000; it cost a RAM upgrade and a weekend of tuning.

2. The tier moved decode, not prefill

Three cold ~90K-token prefills, fresh nonce each time, 90 s cooldown:

Tier Prefill Decode @90K Disk read, first request
8 GiB 194–222 tok/s ~13 tok/s —
30 GiB 743–754 tok/s 21.8–27.9 tok/s 73 GB cold, then ~0.3 GB
35 GiB (full) 747–754 tok/s 25.7–40.4 tok/s same

Prefill did not move between 30 and 35 GiB at all. That settles what the remaining limit is: not the disk. At 30 GiB the same three passes read 8.2 GB, then 0.29 GB, then 0.27 GB off the NVMe and still ran 743–754 tok/s. Disk traffic varied by 30× with no effect on wall time. Prefill at 90K is attention/compute-bound. The ×3.5 win came from getting the decode hot set out of the way, not from making prefill read less.

The one real cost: available fell from 23–24 GiB to 19 GiB, inside the sub-22 GiB band where the kernel starts evicting pages as fast as they fault in. It did not bite — passes 2 and 3 pulled only ~130–180 MB off disk, so the page cache still held the file-tier experts, and 0/3 crashed. But it is why 35 GiB is the ceiling: the next GiB comes out of page cache and buys nothing.

3. The rest of the box

  • Context: 196,608 tokens, --kv int8, with 32K of KV resident in RAM. The 27B also does 192K; the 180B does it with a hierarchy behind it.
  • Vision: a CPU image encoder. It answered a real photograph — a dual-socket motherboard — in 6.2 s, 95 tokens. Setup leaves vision off by default; --vision cpu is the flag that turns it on.
  • Speculative decoding: MTP with --spec 4, min-p 0.5. On the 27B the MTP head accepted 33/36 (92%); on Flash Next the decode speedup is concentrated in code and structured output, not prose.
  • Serving: a systemd user unit, Restart=on-failure, starts at boot. Cold load is 98 s; a warm 27B load is 22 s. The card is exclusive: Strata’s 21 GiB expert cache leaves ~600 MiB free, so the 27B and Flash Next cannot be resident together. The 9060 XT is the escape hatch — Qwen3-8B at 52 tok/s, two 48K slots, on the card Strata does not touch.

The flags that make it fit

The serving engine is Strata, not llama.cpp. The args that matter:

strata serve \
  --pack /mnt/ai-fast/strata-data/packs/unsloth-ud-iq4_xs \
  --native .../Qwen3.8-Flash-Next-UD-IQ4_XS-00001-of-00003.gguf \
  --expert-cache auto \
  --max-context 196608 \
  --kv int8 --kv-resident 32768 \
  --resident-budget-gib 35 \
  --spec 4 --spec-min-p 0.5 --mtp /mnt/ai-fast/strata-data/mtp/rt \
  --vision --vram-reserve-mib 768

--resident-budget-gib must sit under the hard memlock ceiling, or it silently declines to pin. --vram-reserve-mib 768 is the measured fix for the engine’s VRAM accounting; without it, the last allocation can fail. --kv-resident 32768 moves 1.8 GB of KV to RAM, which frees VRAM for the expert cache — a good trade once you have the RAM.

Flash Next is slower per task, often by an order of magnitude, because it reasons before it answers and the 27B does not. That is the trade. If you want the fastest answer to a one-line question, the 27B wins. If you want the answer that is more likely to be correct, the 180B wins.

The single likeliest source of the gap is not the parameter count. It is that Flash Next reasons by default and the 27B runs --reasoning off. The honest experiment — turn reasoning on for the 27B and re-run — is still on the list, and it requires stopping Strata first.

The Diner of the Dead head-to-head

A benchmark is a clean test, but it is not a game. So I ran the same brief through both models from an empty project: the full 7,768-character Diner of the Dead implementation spec, the same 12 MB GLB/texture pack, the same four tools (bash, read_file, write_file, finish), temperature 0.2, and a two-hour wall clock. The only variable was the model. The V620 was handed over between runs with POST /unload and POST /load; nothing else on the box changed.

Two protocol notes. The 27B got a 4,096-token response cap and never hit it. Flash Next’s reasoning is billed against the same budget, and on its first attempts it spent the entire budget thinking and returned no tool call — so the harness doubled the budget after any length-truncated turn (8,192 → 16,384 → 32,768) and told the model to stop planning and take a concrete action. The reasoning stayed on. And the 27B was stopped at 25 minutes, not two hours: it had made 47 identical failed edits to the same file, and the second hour was not going to be different. Flash Next got the full window.

The 27B built a game-shaped thing fast. It had every feature in the spec — three weapons, wall-buys, three enemy types, touch and controller input, points, waves — and it could not run. The parse errors are Godot 4 API errors: intersect_ray() called with five arguments instead of a PhysicsRayQueryParameters3D, instantiate() called on a Node3D, DisplayServer.is_mouse_available() which does not exist in 4.7. It spent the last 11 minutes making 47 identical edits to weapon.gd, getting the same parse error back each time. It never wrote a README.

In the crude harness, Flash Next spent 3.4× the wall clock and 3.8× the output tokens, and it burned two full reasoning budgets (one at 4K, one at 8K) before it wrote a file. Then it built a modular project: eight scenes, 3,131 lines, a 12 KB README, 50 collision boxes, and a wave loop that actually spawns zombies. It also ran cooler — 59–74 °C against the 27B’s 90–100 °C — because only ~3B parameters are active per token. In this workload, the bigger model is easier on the card.

The 27B was not stupid. It produced every feature in the spec, a coherent project.godot with a full input map, and 1,579 lines in 25 minutes. It knew what the game needed. What it could not do was check its API calls against Godot 4.7 — and it could not break out of the loop when the same error came back 47 times. That is less a verdict on the model than on the four tools I gave it.

The retry: both models through a real agent harness

The four-tool loop was judging the 27B on tools I wrote in an afternoon. So I ran the same brief through DSH’s actual agent loop for both models — the same edit, read, todo, line-numbered file views, web access and verification prompt; the same two-hour window, asset pack and spec.

Both finished. The 27B was 14% faster and wrote 10% less code; Flash Next wrote two more scenes and spent six tool calls fetching Godot’s actual source to check API signatures. The 27B also wrote the 5 KB README the spec asked for; Flash Next skipped it. (The 27B README’s controller table is optimistic — its actual pad map is documented below.) The gap that looked like 3.4× wall clock and 3.8× output tokens in the crude harness collapsed to 16% wall clock and 10% code. I stopped each run once its artifact passed the acceptance check; both were polishing, not fixing a broken build.

The four-tool loop’s 47-edit failure was not a model verdict. With edit, line-numbered read and a verification loop, the 27B could see the exact parse error, change one line, and rerun. It took 236 small steps and 65 minutes; my loop gave it a write_file hammer and a nudge, and it spent 47 turns hitting the same intersect_ray error.

So what does the 180B actually buy? Not raw code volume on a one-shot build. It buys the eval score (0.75 → 0.88–1.00), vision, and a 196K context that stays coherent. Those are the capabilities that survived the harness correction. The 27B, given the same tools, is a competent one-shot builder.

The 27B can finish; the 180B can finish more. The harness decides which of those sentences you get to write.

Controller layouts (documentation, not a result)

The builds share assets, not input stacks. The 27B’s pad map is the weak point: all four movement actions sit on left-stick X, so the stick cannot move forward/back independently; look is on LT/RT rather than the right stick; fire is B/L3; reload is A/X; interact is A/Y; weapon cycling is Back/Guide. Flash Next is conventional — left stick move, right stick look, RT fire, LB reload — with one collision: B is bound to both fire and reload, and it has no gamepad sprint. On touch, both use a left-half joystick and right-half drag-look; the 27B’s FIRE is tap-only (its automatic rifle needs repeated taps), while Flash Next’s FIRE presses the real action and holds.

The full mapping, including touch button positions and the 27B’s README-vs-actual discrepancies, is in the controller layouts. These are code-reading notes; the head-to-head results above are unchanged.

Phone playtest (the acceptance test that matters)

Both debug APKs were installed on a Galaxy Z Fold5 and played with a controller.

  • 27B: the player has no collision — it walks through the diner geometry. The death screen shows a RESTART button, but pressing it does nothing. Reload and most other features could not be reached because the pad layout made the game unplayable.
  • Flash Next: almost playable. Right-stick look turns incrementally: each stick movement rotates the camera, but holding the stick does not keep turning. The death-screen restart works, and reload works.

The headless acceptance check proves the project imports, boots and spawns a wave. It does not prove collision, UI buttons or continuous look. The DSH results above are unchanged; this is what the builds do on a phone. Finished is not the same as playable.

What the whole machine buys (measured)

The Diner prompt is the real workload, so I measured that — through DSH, not a bare API probe. Each run started a fresh dsh --profile headless session whose task was the same 7.8 KB Diner spec used in the head-to-head, with the DSH system prompt and tool schemas in the loop. I stopped after the first step, and took the timings from the servers themselves (llama.cpp’s print_timing and Strata’s request log), after a model reload with zero prefix cache.

Cold first DSH step 27B, V620 only Flash Next, whole machine
Model 27B dense, Q6_K 177B-A3B MoE, IQ4_XS
Prompt tokens 8,149 7,957
Prefill 23.94 s / 340.3 tok/s 16.0 s / 497 tok/s
TTFT 24.0 s 16.0 s
Decode 32.66 tok/s 32.5 tok/s
First-step output 109 tok (tool call) 385 tok (thinking + tool calls)
First-step total 27.5 s 29.7 s
Observed junction 90–100 °C 60–75 °C
Prefix cache 0 0

TTFT is server prompt-eval plus one decode step. The 2.4% prompt-token difference is the DSH system prompt naming a different model.

Three things fall out of that table.

1. The 180B is not slower to first token — it is faster. On the same real prompt, the 177B model prefills at 497 tok/s against the dense 27B’s 340 tok/s, and reaches its first token 8 seconds sooner. Decode is a tie: 32.5 vs 32.66 tok/s. The reason is sparsity: only ~3B parameters are active per token, so the bigger model does less prefill math than the dense 27B. The 32 GB card alone could never hold it; the RAM tier and NVMe are what let the sparse model be faster than the smaller dense one.

2. What that buys is capability, not throughput. The 180B is the model that scored 0.75 → 0.88–1.00, sees images and holds 196K context. The 27B is the simpler machine — 22 GB of VRAM, one binary, no RAM tier — and it is the one that cannot run the 177B at all. The whole machine’s payoff is that the capability arrives without a TTFT penalty; on this prompt it is a TTFT win.

3. The first step still takes longer, because the 180B thinks more. It generated 385 tokens (reasoning plus tool calls) against the 27B’s 109, so its first step finishes in 29.7 s vs 27.5 s even with the faster TTFT. That is the quality/speed trade in one line: the 180B gets to the first token sooner, then spends more tokens before it acts.

The trade in one line: the whole machine does not buy raw tok/s. It buys a 6.5× larger model at the same decode rate and a faster first token, paid for in 64 GB of RAM, 34 GiB of it pinned, an 87 GB model on NVMe, and a much more complex serving stack.

The warm-prefix case is different again. Once the DSH system prompt/tools/spec prefix is cached, TTFT collapses: the 27B’s warm request had 0.22 s prompt-eval for 4 new tokens, and Flash Next’s warm decode measured 47 tok/s on a cached prompt. The cold table above is the honest first-request cost; the warm numbers are what repeated DSH sessions actually feel like.

So, in one paragraph: both models decode at essentially the same rate — 32.5 vs 32.66 tok/s. Flash Next prefills ~46% faster (497 vs 340 tok/s), uses ~2.4% fewer prompt tokens (7,957 vs 8,149) on the same DSH prompt, and runs 15–40 °C cooler (60–75 vs 90–100 °C). And it is the much more capable model: 177B total / ~3B active vs 27B dense, with the better eval score, vision and 196K context. That is what the whole machine buys: more model, faster prefill, fewer prompt tokens and lower temperature, at the same decode speed.

Caveats: one cold run per model; timings are rounded server-log values; the 27B was thermally throttling at 90–100 °C; Flash Next’s expert cache hit 84.5% on the cold request; and first-step output lengths differ, so decode rate — not total tokens — is the comparable metric. The 90K prefill figure elsewhere in this post is a warm, long-context probe; this table is the cold, real-prompt measurement.

What it costs

  • Disk: 87.25 GiB for the model, plus the engine and the vision encoder. Budget ~95 GB, and keep it on an SSD — the file tier is memory-mapped.
  • RAM: 35 GiB page-locked, plus page cache. 32 GB is not enough; 64 GB is the operating point.
  • Speed: 12–33 s per short task against 0.7–2.9 s for the 27B. In the Diner build, the mean response was 48 s and the worst was 267 s. You feel it in a chat loop. You stop feeling it when the task is a 40-minute refactor.
  • Exclusivity: one big model on the V620. The 27B cannot load while Strata holds the card. Plan the switch, or put the small model on the second GPU.
  • Stability: the stock-voltage run was 0/3 crashes, against 1/3 and 2/3 before. That is n=3 — strongly suggestive, not proof. The pin fix removed the verify timeouts; the engine watchdog can still abort under memory starvation.
  • Thermals: the V620 is a passively cooled server card behind a printed shroud and a manual fan wall. It throttles itself near 100 °C junction. On a warm start the 27B hit 100 °C at 244 W; the first long step crawled, then the card settled at ~94 °C and ~32 tok/s. The 180B’s October baseline was 78 °C at 252 W after the repaste. If the card idles hot, check the fan controller before blaming the model.
  • RAM speed: 29 GB/s means DOCP is still off. Re-enabling it is a separate experiment and should not share a window with a stability test.
  • RAM integrity: 3 of 9 runs flagged exactly one byte at a fixed page+offset, all near an OOM kill; six consecutive runs since are clean. A MemTest86 pass is still owed.
  • Quantization: IQ4_XS is a 4-bit build. It passed every task the 27B passed and two it did not, but “4-bit 177B” is not “BF16 177B”. The PLE table is the part I would quantize last.

Why this is “expanding integration”

The 27B post was about a card. This one is about the space between the card, the RAM, the disk, and the second GPU. The model did not get faster because I bought a bigger GPU; it got possible because the serving engine stopped treating VRAM as the only place a weight can live.

That is the actual upgrade: a memory hierarchy, a memlock ceiling, and a scheduler that knows which expert is hot. The 180B is not running on a $376 card because the card is magic. It is running because 21 GiB of it is on the card, 34 GiB is in RAM, the rest is on an NVMe, and the engine moves the right piece to the right place at the right time.

The 27B proved the hardware. The 180B proves the integration.

Software is easy. Buy more hardware — then teach it to use all of it.
