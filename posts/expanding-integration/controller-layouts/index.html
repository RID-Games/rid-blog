Diner of the Dead — controller layouts as shipped

Read-only inspection of the two DSH builds. No game files were changed, and the
head-to-head results are unchanged. This documents what each build actually
binds and consumes, not what its README claims.

Sources: project.godot input maps, player.gd, touch_controls.gd,
weapon.gd, main.gd, hud.gd in each project.

The movement mapping is the important one. player.gd calls
Input.get_axis("move_left", "move_right") and
Input.get_axis("move_forward", "move_back"). Because all four actions sit on
axis 0 with conflicting signs:

  • push left → move_forward + move_right → strafe right and forward;
  • push right → move_back + move_left → strafe left and back;
  • push up/down → no action at all.

The left stick cannot move forward/back independently. Keyboard WASD still works
because those are separate key events; touch movement bypasses the actions via
set_touch_move().

The README’s controller table claims left-stick move, right-stick look, R2 fire,
L1/X reload, A/Y interact, LB/RB cycle. The actual map is left-stick X movement,
trigger look, B/L3 fire, A/X reload, A/Y interact, Back/Guide cycle.

Touch

  • Left half: floating joystick, 120 px base, 60 px knob, 120 px travel.
  • Right half: drag to look; drag right looks left (“grab the world”).
  • Bottom-right: FIRE (140 px), RLD (100 px) to its left, USE (100 px) further
    left.
  • Bottom center-right: 1 / 2 / 3 weapon buttons (48 px).
  • Touch UI is shown only when DisplayServer.is_touchscreen_available(); there
    is no desktop toggle.
  • FIRE is tap-to-shoot, not hold-to-fire. The button calls
    weapon.start_firing() directly, but player.gd polls the fire action every
    physics frame and calls stop_firing() because the touch button never presses
    that action. The pistol and shotgun fire once per tap; the automatic rifle
    needs repeated taps.
  • No touch pause. Pause is Start/Esc only; the HUD label even says
    “PAUSED — Esc to resume”.

There is no gamepad sprint; sprint is keyboard Shift only. The README was
not written for this build (the DSH artifact has no README).

Touch

  • Left half: floating joystick, 144 px ring, 72 px knob.
  • Right half: drag to look.
  • Bottom-right: FIRE (172 px), RELOAD (108 px) to its left, USE (108 px)
    above FIRE.
  • Top-right: 1 / 2 / 3 weapon buttons (60 px).
  • Touch UI auto-enables on a touchscreen and can be toggled with F9 on desktop;
    it also disables mouse-from-touch emulation so the FIRE button does not
    double-fire through LMB.
  • FIRE/RELOAD/USE and the weapon buttons press the real input actions and release
    them on finger-up, so hold-to-fire works, including the automatic rifle.
  • No touch pause button. The pause menu has RESUME/RESTART buttons, but it
    only opens via the pause action (Start/Esc).

Phone playtest (2026-11-10)

Installed from the two debug APKs on a Galaxy Z Fold5, with a controller:

  • 27B: no player collision — walks through the diner geometry. The death-screen
    RESTART button is visible but inert. Reload and most features could not be
    reached because of the pad map above.
  • Flash Next: almost playable. Right-stick look is incremental: it turns on
    each stick movement but does not keep turning while the stick is held. Reload
    works, and the death-screen restart works.
  • The incremental look matches the code: Flash Next applies look in
    _unhandled_input on InputEventJoypadMotion, so a held, unchanging axis
    produces no further events. Continuous look would need per-frame axis polling.
  • The 27B collision code and the restart call both exist in the source; the
    failures are runtime/UI behavior, not missing functions.

Caveats

  • This is static code reading. Action deadzones are 0.5 unless noted; the look
    sticks use raw-axis deadzones of 0.1 (27B) and 0.18 (Flash Next).
  • The 27B’s pad movement is expected to be unusable; confirm with a real
    controller before treating it as a playable layout.
  • The 27B’s keyboard sprint event is malformed (shift_pressed=true, no keycode),
    so treat Shift-sprint there as unverified.
  • Neither build exposes a touch pause control; on a phone, pausing needs a
    controller Start button (or Android’s back handling, which neither
    implements explicitly).
